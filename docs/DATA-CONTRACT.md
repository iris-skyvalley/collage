# The data contract

PRD §9 is the only requirement in this build driven by work outside it: the
riff layer is being built separately, and this build's whole obligation to it
is that every piece persists as a parameterised version with a parent field.

It has to be right in the first build, because retrofitting it means migrating
everything users have made. So it is enforced in code — `parseComposition` and
`assertVersionContract` in [`shared/src/version.ts`](../shared/src/version.ts),
called on every write — rather than documented and hoped for.

## The record

```
Version
  id                 short, URL-safe; this is the share URL
  parent_id          nullable — always written, never read in v1
  root_id            nullable
  created_by         anonymous session id, or user id after a claim
  theme              the tray the piece was composed from
  substrate          { stock, colour, texture }
  palette
  layers[]           ordered
    id
    fragment_ref     { source, id, uri?, credit?, w, h }
    transform        { x, y, scale, rotation, z, flipX? }
    verbs[]          { verb, params }
    placed_at_ms     when it landed, relative to the session
  render_hashes      { piece, story, replay }
  recipient          nullable — carried, never read in v1 (PRD §13 Q3)
  created_at
```

## The five non-negotiables, and how each is held

**`parent_id` and `root_id` exist and are written from day one.**
`parseComposition` rejects a composition that omits either, rather than
defaulting them — a default would let a client stop sending them and nobody
would notice until the riff layer tried to read them. `assertVersionContract`
additionally refuses a version with a parent but no root, and a rootless
version claiming someone else's root. On write, the server derives `root_id`
from the parent's own root rather than trusting the client's copy, so a chain
of any depth resolves to one root.

**Fragments are referenced, never flattened.** A `data:` URI anywhere in a
`fragment_ref` is rejected at parse *and* at the contract check. Uploaded
photos live in the device's IndexedDB and are pushed to the server on share,
which gives the ref a URL — still a reference, and the pixels still never enter
the record.

**Verbs are stored as parameters, never baked into pixels.** Verb params accept
only numbers, strings, booleans and number arrays, and a string beginning
`data:` is rejected. The semantic cut is the interesting case: a segmentation
model returns a mask, which is pixels, so the verb stores a `mask_ref` and the
mask is resolved at render time exactly as a fragment is.

**Layer order and timing are retained.** `z` is explicit and must be distinct
across a version — ambiguous order is rejected, because the order *is* the
replay and will be the diff. `placed_at_ms` survives the round trip.

**A version is reconstructable from its record alone.** `parseComposition` is a
fixed point: parsing a parsed composition returns exactly the same object. The
renderer takes a composition and nothing else. Fragment ids are seeds, so any
generated fragment can be regenerated byte-identically from its id; verb seeds
are derived from layer ids, so a torn edge tears the same way on every machine
and at every raster size.

## What the riff layer will need to do

Read versions and write children. Concretely:

```sql
-- a piece's direct riffs
SELECT id FROM versions WHERE parent_id = ?;
-- everything descended from one origin
SELECT id FROM versions WHERE root_id = ?;
```

Both columns are indexed. Writing a child is the same `POST /api/versions` the
editor already uses, with `parent_id` set — which is exactly what link arrival
does today, so the path is already exercised in production traffic before the
riff layer exists.

## What is deliberately not in the record

- Rendered pixels. `render_hashes` points at content-addressed blobs; they are
  a cache and a preview, and deleting them costs nothing but a re-render.
- Anything about how a piece was shared, or by whom. That lives in events.
- Fork counts, lineage display, attribution surfaces — PRD §3 non-goals. The
  data supports them; the product does not show them.
